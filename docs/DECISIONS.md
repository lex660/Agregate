## ADR-006. Сохранить архитектуру новой версии, не переписывать

**Дата:** 12.10.2026

**Контекст.** В репозитории уже есть ветка `rebuild-eleventy` (PR #1), сделанная
предыдущей сессией: статический сайт на Eleventy, расчёт в браузере, 26 проходящих
тестов, тарифы с источниками и датами проверки. Я проверил её лично: `npm test`,
`npm run build`, `npm run check` — всё проходит.

**Варианты.**
1. Принять существующую архитектуру и доводить её до production.
2. Переписать на другом стеке (Astro, Next.js, чистая статика без генератора).
3. Вернуться к схеме с бэкендом и живым парсингом.

**Выбор:** вариант 1.

**Причина.** Стандарт проекта — «простота важнее модности», и существующее решение ему
соответствует: Eleventy с одной зависимостью, расчёт в браузере, никакого бэкенда,
который можно уронить. Главное же — качество содержания: ставки не выдуманы, у каждой
есть `source` и `verified_at`, лимиты тарифов проверяются до расчёта, а компании без
подтверждённых условий показываются без цифр, а не с придуманными. Это ровно тот дефект,
из-за которого старый воркер показывал пользователю недоступный ему тариф «Гарант» как
самое выгодное предложение. Переписывание уничтожило бы проверенные данные и тесты без
выгоды. Вариант 3 отклонён: живой парсинг на запрос пользователя означает, что сайт
падает вместе с сайтом любой компании, и перепубликует чужие данные автоматически —
хуже и технически, и юридически.

## ADR-005. Сменить название сайта с «Сравни рассрочку»

**Дата:** 12.10.2026

**Контекст.** В ветке `rebuild-eleventy` сайт назван «Сравни рассрочку», в кандидатах
на домен был `sravnirassrochku.ru`. «Сравни» — бренд и товарный знак действующего
крупного финансового агрегатора Сравни.ру, работающего в той же тематике (сравнение
финансовых продуктов).

**Варианты.**
1. Оставить «Сравни рассрочку».
2. Переименовать в описательное название без чужих товарных знаков.
3. Сохранить преемственность со старым брендом «Vsay».

**Выбор:** вариант 2, с оговоркой в пользу 3, если владелец возвращает старый домен.

**Причина.** Название, начинающееся с «Сравни», в финансовой тематике создаёт реальный
риск претензии по товарному знаку — а для проекта, который только выходит в production,
это несоразмерный риск при нулевой выгоде. Свободные домены, проверенные по whois
12.10.2026: `halal-rassrochka.ru`, `halalrassrochka.ru`, `rassrochka-bez-riba.ru`,
`murabaha-calc.ru`, `bezriba.ru`. Рекомендую `halal-rassrochka.ru`: описательно,
совпадает с поисковыми запросами аудитории, не содержит чужих знаков. Если владелец
восстанавливает `vsay-rassrochka.ru` (см. ADR-001), вопрос снимается — остаётся
прежний бренд, что ещё лучше для SEO. Я не регистрирую домены сам: это платёж.

## ADR-004. Сохранить Яндекс.Метрику, но загружать её только после согласия

**Дата:** 12.10.2026

**Контекст.** Счётчик `104202450` используется и в старой, и в новой версии; в старой
включён `webvisor: true` и счётчик грузится сразу при открытии страницы. По практике
применения 152-ФЗ аналитику включают после явного согласия пользователя, а кнопка отказа
должна быть так же заметна, как кнопка согласия (см. `docs/RESEARCH.md`, раздел 2.2).

**Варианты.**
1. Оставить как есть.
2. Убрать аналитику совсем.
3. Оставить Метрику, но грузить после согласия и выключить вебвизор.

**Выбор:** вариант 3.

**Причина.** Аналитика проекту нужна: без неё не понять, какие регионы и суммы
востребованы, и не на чем строить разговор с компаниями о партнёрстве. Но текущая
реализация — самый дорогой риск по 152-ФЗ на сайте, который в остальном вообще не
собирает персональных данных (нет форм, нет регистрации, расчёт идёт в браузере).
Терять это преимущество из-за счётчика неразумно. Вебвизор выключается: запись действий
пользователя трактуется строже обычной статистики, а пользы для этого сайта почти не даёт.

## ADR-003. Основной хостинг — Yandex Object Storage, запасной — Timeweb Cloud S3

**Дата:** 12.10.2026

**Контекст.** Нужен российский хостинг статического сайта до 1 000 ₽/мес, с автодеплоем
из GitHub и минимумом ручных действий владельца. Сравнение и цены — `docs/RESEARCH.md`,
раздел 5.

**Варианты.** Yandex Object Storage · Timeweb Cloud S3 · Selectel Object Storage · VPS.

**Выбор:** Yandex Object Storage основным, Timeweb Cloud S3 запасным.

**Причина.** Сайт весит около 1 МБ, и даже при 10 000 посетителей в месяц трафик
укладывается в бесплатный лимит Yandex (1 ГБ хранения, 100 ГБ трафика, 100 000 GET
в месяц) — то есть реальная стоимость близка к нулю, а бюджет 1 000 ₽ ограничением
не является. Выбор определялся не ценой, а надёжностью и зрелостью: у Yandex Cloud есть
Certificate Manager с бесплатным автопродлеваемым сертификатом Let's Encrypt, что снимает
с владельца заботу о HTTPS навсегда. Timeweb Cloud (79 ₽/мес) оставлен запасным, потому
что его панель заметно проще, и если настройка сервисного аккаунта и ключей в Yandex
окажется для владельца слишком тяжёлой, переход будет дешёвым — см. ADR-002.
VPS отклонён: при цене 200–400 ₽ он требует от владельца администрирования ОС и
продления сертификатов, что прямо противоречит цели проекта.

## ADR-002. Деплой через S3-совместимый API с endpoint в переменной

**Дата:** 12.10.2026

**Контекст.** Выбор хостинга сделан (ADR-003), но владелец ещё не оплатил его и может
передумать. Текущий workflow в `rebuild-eleventy` жёстко зашивает endpoint
`storage.yandexcloud.net`.

**Варианты.**
1. Оставить жёстко зашитый Yandex.
2. Вынести endpoint и регион в переменные репозитория.
3. Поддержать оба провайдера отдельными job'ами.

**Выбор:** вариант 2.

**Причина.** Yandex Object Storage, Timeweb Cloud S3 и Selectel — все S3-совместимые,
поэтому один шаг `aws s3 sync` работает с любым из них. Вынеся endpoint в переменную,
мы превращаем выбор провайдера из архитектурного решения в одну строку настройки:
если владельцу не подойдёт Yandex, переезд будет стоить правки переменной, а не
переписывания деплоя. Вариант 3 даёт то же самое, но удваивает объём workflow,
который придётся поддерживать.

## ADR-001. Домен: рекомендую восстановить старый, но решение за владельцем

**Дата:** 12.10.2026

**Контекст.** Вводные к задаче говорят «нужен новый домен». При проверке whois
12.10.2026 выяснилось, что старый домен `vsay-rassrochka.ru` не потерян:
`paid-till: 2026-09-23`, **`free-date: 2026-10-27`**, регистратор REGRU-RU,
NS = `ns1/ns2.expired.reg.ru`. То есть домен в периоде, когда его ещё может вернуть
прежний владелец. После 27.10.2026 он освобождается и может быть занят кем угодно.

**Варианты.**
1. Восстановить `vsay-rassrochka.ru` у reg.ru до 27.10.2026.
2. Зарегистрировать новый домен (169 ₽ по акции reg.ru на 2026 год).
3. Остаться на `lex660.github.io/Agregate` без своего домена.

**Выбор:** рекомендую вариант 1; при отказе — вариант 2. Код написан так, что выбор
на него не влияет: адрес сайта задаётся переменной `SITE_URL`.

**Причина.** Вводные, похоже, исходили из того, что домен потерян безвозвратно — это
не так, и у владельца есть 15 дней. Восстановление сохраняет историю индексации в Яндексе,
уже подтверждённые права в Вебмастере и Search Console (файлы лежат в репозитории),
внешние ссылки и накопленную статистику Метрики. Новый домен означает начать
индексацию с нуля в нише, где поисковый трафик — основной канал. Вариант 3 отклонён
как постоянное решение: адрес вида `lex660.github.io/Agregate` не подходит сайту про
чужие деньги, но остаётся как рабочий временный адрес и демо.

**Это не моё решение:** регистрация и восстановление домена — платёж, его делает
владелец. Моя часть — не блокировать проект ожиданием: сайт будет работать на адресе
GitHub Pages, а подключение домена сведётся к изменению одной переменной и DNS-записи.

**Срок истекает 27.10.2026.**
